# ODB 高级形式化说明

适合：计算机、数学、系统架构和审计实现读者。本文只公开协议与不变量，不公开推理机内部算法。

## 1. 对象模型

设系统状态为

`S = (C, G, W, I, R, A, H)`

其中：

- `C`：命令集合；
- `G`：货物及其谱系集合；
- `W`：工作流和工序约束；
- `I`：身份、租约和版本集合；
- `R`：路条、车票、收条和回执集合；
- `A`：审计证据集合；
- `H`：仓库、道路、信号和恢复检查点集合。

系统不把自然语言字符串直接视为可执行命令。入口必须先生成结构化的前端工单，再由后端总控生成业务经停表。

## 2. 五级生产树

生产树定义为有根有向树 `T=(V,E)`，层级顺序为：

`TOTAL_CONTROL -> LAYER_CONTROL -> MODULE_CONTROL -> WORKSHOP_CONTROL -> FUNCTION_COMPONENT`

每条物理运输边 `(u,v)` 必须满足 `parent(u)=v` 或 `parent(v)=u`，且由登记的协议端点、运行实例、回执返回边和失败终态共同构成。跨层直接工作站调度和无父节点的边均非法。

命令沿树向下传播，回执沿已声明路径反向上行。业务载荷不得全局广播；高危摘要可在完成本地冻结、反向上报和逐级向下广播后，沿高危专用树形道路进入业务层邮政隔离区。

## 3. 部门不变量

对任意节点 `v`，其五部职责必须满足：

1. `SelfCheck(v)` 只执行边界检查、放行、拒绝和冻结，不执行业务计划。
2. `Audit(v)` 只追加无正文证据，不改变生产状态，不作业务决策。
3. `Control(v)` 负责计划、激活、停止和有界恢复，不执行功能组件内部计算。
4. `Ledger(v)` 负责持久任务状态、结果、身份、车票和核销，不选择业务政策。
5. `Communication(v)` 负责道路健康、交通信号和动力载具，只接受已放行的直接边车票。

自检部和审计部属于上层监督；控制、通信和账房属于下层生产职能。行政归属树用于管理，不等于可以绕过生产路径的运输路线。

## 4. 工单、路条与车票

后端总控产生业务经停表 `O`：

`O = (activation_set, precedence_graph, parallel_groups, receipt_requirements)`

起点账房根据封存的 `O` 与当前树形交通状态产生端到端路条 `L`。路条的目标不可由交通部修改。

当前节点账房产生直接边车票 `K_i`，满足：

`K_i = (origin_i, destination_i, transfer_nodes_i, L_id, cargo_id, command_id, validity, release)`

并且 `edge(origin_i,destination_i) ∈ E`。动力载具调用的必要条件是 `release(K_i)=true` 且车票未关闭。通信部不得从 `L` 直接发车，也不得改变 `O` 或 `L` 的业务目标。

最终接收条件：

`destination(K_last) = destination(L)`

且货物、命令和车票身份绑定通过接收方自检。否则拒绝入城；拒收货物进入接收方冻结区，不获得拆包许可。

## 5. 状态与断点恢复

货物状态至少区分：`CACHED`、`WAITING`、`IN_TRANSIT`、`DELIVERED`、`BOUND`、`UNPACKED`、`PROCESSING`、`PACKED`、`FROZEN`、`COMPLETED`。

运输和车间边界必须持久化：车票签发、放行、载具调用、在途、到站自检、过路章、下一票签发、入城、拆包、开工、收工、封包及票据绑定。

令 `checkpoint(S)` 为账本投影出的最近有效边界。恢复函数满足：

`recover(S) = continue(checkpoint(S))`

而非从入口重放。对已经产生副作用的阶段，恢复必须幂等：

`effect_count(recover(S)) = effect_count(S)`

除非该阶段明确标记为失败且允许局部重试。函数、Qwen 候选和已关闭车票不得因恢复被重复调用或重发。

## 6. 仓库与故障

仓库分为缓存仓库、长期仓库和冻结仓库。缓存用于短暂拥堵，长期仓库用于持续等待或停机，冻结仓库用于高危货物留证。仓库满载触发相应拥堵或全局停机警告，不得用另一个仓库掩盖容量问题。

审计管道与自检管道分离。自检管道不畅通时，相关区域必须隔离；审计管道不畅通但自检畅通时可继续有限运行，同时提升审计维修优先级。运维和开发可以使用专用逻辑公路，但其一般自检和审计证据仍按规定进入对应管道。

## 7. 版本与扩张

开发层是与业务层同级的支持层，无额外权限。扩张请求必须经过既有职责冲突预检：

- 纯新增：不得与现有权限重叠；
- 权限迁移：恰好一项去除和一项新增；
- 纯删除：允许只有去除项；
- 无权限变化：增删集合均为空。

开发、冷运维、热运维分别表示吸收新能力、恢复既有能力和重构既有能力。新版本使用新身份，旧版本保留；试用成功后才可接受切换，失败则丢弃新版本并回退。

## 8. 形式化验收条件

一次自动化验收必须满足：

- 初始启动命令数为 `1`；
- 启动后操作员介入数为 `0`；
- 外部人工交接数为 `0`；
- 终态为明确的完成、等待、拒绝、冻结或人工复核状态；
- 每个激活接口都有发送端、接收端、运行实例、回执返回和失败终态；
- 每个变更覆盖所有发现的运行载体和边，样例或模板不能代替全量迁移。

## 9. 公开与保密边界

公开内容是上述对象模型、职责、协议、状态、不变量和脱敏证据。以下内容不在本文披露：变量引擎内部算法、模型提示词和会话分配、密钥与令牌、内部数据库结构、未脱敏业务正文以及可直接复刻核心的完整代码。
